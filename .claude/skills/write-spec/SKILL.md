# 仕様書・設計書の作成規約

このリポジトリでは、実務レベルで詳細な設計ドキュメントを `docs/` 配下に整備する。
ドキュメントは「コードを読まなくても仕様が分かる」粒度を目指す。

## ドキュメント一覧

| ファイル | 内容 |
|----------|------|
| `docs/01_要件定義.md` | 機能・非機能要件の定義（何を作るか） |
| `docs/02_基本設計書.md` | 画面・DB・処理の設計（どう作るか）※今後作成 |
| `docs/03_詳細設計書.md` | クラス・関数レベルの設計 ※今後作成 |

## 作成・更新時の規約

1. **見出し構成は既存ドキュメントと揃える**（番号見出し、表形式、文書管理情報）
2. **文書管理情報を先頭に置く**（文書番号・バージョン・作成日・ステータス・変更履歴）
3. **機能にはIDを振る**（例: F-01〜、画面は S-01〜）
4. **受入条件を明記する**（「〜できること」形式でテスト可能に）
5. **優先度を付ける**: 必須 / 重要 / 任意
6. **コードを変更する前に**、該当する設計書を更新する
7. **業務ルール（打刻順序・集計式など）は必ず文書化し、実装と一致させる**

## テンプレート（要件定義・基本設計共通の基本形）

```markdown
# タイトル

| 項目 | 内容 |
|------|------|
| 文書番号 | XX-xxx |
| バージョン | x.x |
| 作成日 | YYYY-MM-DD |
| ステータス | レビュー中 |

## 変更履歴
| 版 | 日付 | 変更内容 | 承認 |
|----|------|----------|------|
```

## 注意点

- 仕様変更時は、コードの変更だけでなく**設計書の更新も忘れずに行う**こと
- 要件定義の機能ID（F-xx）はコードの機能やテストと対応付けて管理する
- 図（ER図・画面遷移図）は Mermaid 記法で書くと Git 差分が取りやすい
