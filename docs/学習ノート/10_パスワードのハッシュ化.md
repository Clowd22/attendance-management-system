## 質問

> レビューと解説をしてほしい。そして、ここでパスワードをなぜハッシュ化するのかという話も含めて説明してほしい。特にパスワード保存する目的とそのパスワードの利用方法も触れてください。

## 回答の要旨（結論）

パスワードは**平文で保存せず、ハッシュ化（一方通行変換）して保存**する。目的は「次回ログイン時に、入力されたパスワードが本人のものか照合する」ためで、元のパスワードを復元できる必要はない。照合は `verify_password()`（bcrypt の verify）で行う。

## なぜハッシュ化するのか

平文で保存すると、DB が漏えいした瞬間に全員のパスワードが丸見えになる。

ハッシュ化は「一方通行の変換」。

| | ハッシュ化 | 暗号化 |
|---|---|---|
| 方向 | 一方通行（元に戻せない） | 双方向（復号できる） |
| 用途 | パスワード保存 | データの秘匿 |
| 鍵 | 不要 | 必要 |

パスワード保存に「復元できない」ハッシュを使うのは、「復元できるなら漏えい時に元に戻されてしまう」から。照合さえできればいいので、戻せないハッシュで十分。

## パスワード保存の目的

「次回ログイン時に、入力されたパスワードが本人のものか照合する」ためだけ。

「パスワードそのものを知る」必要はなく、「入力値が登録時の値と一致するか」を判定できれば十分。だから元のパスワードは捨て、ハッシュだけ保存する。

## パスワードの利用方法（認証の流れ）

```
【登録時】
平文 "password123"
   │ hash_password()
   ▼
ハッシュ "$2b$12$...ランダムsalt...暗号文字列"
   ▼
DB の employees.password_hash に保存（平文は捨てる）

【ログイン時】
入力 "password123" → verify_password(入力, 保存ハッシュ)
   ▼
bcrypt がハッシュ内の salt を読み取り、入力値を同じ salt でハッシュ化して比較
   ├─ 一致  → True（ログイン成功）
   └─ 不一致 → False（ログイン失敗）
```

## salt（ソルト）の話

- bcrypt はハッシュ化の前に salt（ランダムな値）を混ぜる。
- だから同じパスワードでも毎回違うハッシュ文字列になる。
- レインボーテーブル攻撃（事前計算したハッシュ表との照合）や「同じハッシュ＝同じパスワード」と見抜く攻撃を防ぐ。
- これが、`verify_password()` が単純な文字列比較ではなく bcrypt の `verify()` に任せている理由。

## C# / SQL Server との対応

| C# / SQL Server | 今回 |
|-----------------|------|
| ASP.NET Core の `PasswordHasher<T>` や BCrypt.Net | `pwdlib`（`PasswordHash`） |
| `HashPassword()` / `VerifyHashedPassword()` | `hash_password()` / `verify_password()` |

「ハッシュ化して保存、verify で照合」の流れはまったく同じ。
